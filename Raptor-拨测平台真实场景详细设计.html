01 · CAPACITY SEMANTICS

先定义 TPS，否则所有数字都不可信

测试套是调度单位，HTTP Case 是容量单位。一个测试套包含多个 Case；Case 可以串行、并行或按依赖 DAG 执行。

HTTP TPS = 每秒实际发出的 Case HTTP 请求数
Suite Run TPS ≈ HTTP TPS ÷ 平均每套 Case 数
示例：平均 5 Case/套时，10,000 HTTP req/s ≈ 2,000 个测试套执行/s
在途数：10,000 req/s × 200ms 平均耗时 = 2,000；3s 超时上界 = 30,000

控制面

测试套 CRUD、版本发布、Token、调度策略、权限；通常几十到几百 QPS，不按 10k 设计。

执行面

Scheduler、Kafka、Go Worker、HTTP Client、Result Pipeline；10k TPS 的主要承载面。

结果面

每 Case 明细最高 8.64 亿条/天；必须从 MySQL 控制库拆出独立高吞吐存储。

为什么 Case 明细不建议只存 MySQL：持续 10,000 req/s = 864,000,000 条/天。即使每条压缩后只有 300B，也约 259GB/日，尚未计算索引、Binlog、复制和备份。MySQL 保存控制数据和 Suite 摘要；Case 明细通过 Kafka 微批写入 ClickHouse，响应证据只保存截断/脱敏摘要，大体积放对象存储并设置 TTL。
03 · SCHEDULING & ROUTING

测试套如何被调度并路由到正确执行池

Scheduler 不执行 HTTP，也不直接挑某个 Pod；它只解析配置、生成稳定 executionId、确定逻辑执行池，并写入对应 Kafka Topic。

扫描到期计划

ElasticJob 按 suite_id 哈希分片，批量查询 enabled=1 且 next_fire_time≤now；行锁/乐观版本更新下一次时间，防止重复调度。

创建稳定执行标识

executionId = UUIDv5(suiteId + version + scheduledAt + probePoint)。先 INSERT probe_suite_execution，唯一键吸收主备调度器重复。

解析路由

根据 environment、network_domain、connectivity matrix、required labels 解析 executor_pool_id；无 REACHABLE 池则标记 UNSCHEDULABLE，不把网络未开通当应用失败。

发布命令

写 probe-command-{network-domain}；Key 使用 poolId + targetHostHash，使相同目标的配额和局部顺序落在稳定分区。

Worker 竞争 Lease

同一 Pool Consumer Group 领取命令，CAS 更新 execution: PENDING→RUNNING、worker_id、lease_until；失败说明已被其他 Worker 获取，直接幂等跳过。

选择：固定逻辑执行池 + 动态 Worker Pod

执行池按 PROD/NON_PROD、网络域、区域固定；Pod 是长期运行的暖实例，由 Deployment + KEDA/HPA 增减。路由稳定、连接池可复用、扩容成本可控。

不选：每次 Suite Run 创建 Job/容器

K8S 调度和镜像启动通常需要秒级；10k TPS 会压垮 API Server、Scheduler、镜像仓库和 CNI，且无法复用 DNS/TLS/HTTP 连接。

执行节点到底固定吗？逻辑 Pool 固定，物理 Node 相对稳定，Worker Pod 动态。任务不绑定具体 Pod；同 Pool 内任意健康 Worker 都可执行。只有需要固定源 IP 时，Pool 绑定专用 Node Group/NAT Gateway，而不是固定 Pod IP。

连通机制

  • 同 VPC/集群：Cluster DNS + Service/Ingress。
  • 跨 VPC：VPC Peering/Transit Gateway + 私网 DNS 转发。
  • 必须固定源 IP：专用 Node Group + SNAT/NAT Gateway 地址池。
  • NetworkPolicy 默认拒绝，只放通批准的域名/CIDR/443。
  • 发布前执行 DNS→TCP→TLS→HTTP 四阶段网络准入。

端口与连接

  • 优先 HTTP Keep-Alive 和连接池，避免 10k 新连接/s。
  • 限制每目标 maxConns、maxIdleConns 和并发，防止压垮单服务。
  • 无 Keep-Alive 时重点验证源端口/NAT 表、SYN backlog、TLS CPU。
  • DNS 使用本地缓存但尊重 TTL；必须防 DNS rebinding。
  • 响应体最多读取 64KB，超出截断，防带宽和内存放大。
带宽假设：平均请求 2KB + 平均响应 8KB + TLS/网络开销 20% ≈ 12KB/请求
全局带宽：10,000 × 12KB ≈ 120MB/s ≈ 960Mbps；按 2 倍冗余规划 ≈ 2Gbps
节点规划：6 台 × 8 vCPU/16GiB/10Gbps；每台约 1,667 req/s，仅约 160Mbps 平均业务流量
结论：建议 10Gbps NIC 不是因为平均带宽需要，而是为突发、东西向流量、重传和共享 CNI 留余量；真正瓶颈更可能是连接数、PPS、NAT、DNS 或目标服务配额。
规格必须跟真实响应体校准：如果平均响应不是 8KB 而是 64KB，全局平均带宽会超过 6Gbps，6×10Gbps 节点仍可能够，但 CNI/NAT/目标入口必须重新压测；不能只拿 10Gbps 网卡标称值作证明。
05 · WORKER EXECUTION ENGINE

一个 Worker 如何执行包含多个 Case 的测试套

Worker 获取指定 suite_version 的不可变配置，构建 Case DAG；配置按版本缓存，禁止每次执行都回源 MySQL。

模式语义适用场景限制
SERIAL按 sort_order 逐个执行；前置 Case 可提取变量供后续 URL/Header/Body 使用。登录→查询→校验、存在数据依赖。任一 Case 失败时按 on_failure=STOP/CONTINUE；Suite 总超时硬限制。
PARALLEL无依赖 Case 同时执行；每 Suite 使用 semaphore 限制 max_parallelism。多个独立健康接口。默认最多 10；共享变量禁止并发写，目标级限流优先。
DAG拓扑排序；同一层并发，层间等待；失败向下游传播 SKIPPED_DEPENDENCY。复杂业务链路兼顾并发。发布时检查环；最大 100 Case、最大深度 20。

获取配置

Command 只带 executionId、suiteId、version、deadline、poolId。Worker 从本地 LRU/Redis Config Cache 按 content_hash 获取不可变快照。

准备上下文

创建 suite context 和总 deadline，换取短期 Token，验证域名/IP、目标配额、响应上限；不将 Token 写入上下文日志。

执行 Case

每 Case 有独立 timeout；异步 HTTP Client 记录 DNS/TCP/TLS/TTFB/Total；GET/HEAD 可按策略重试，POST 默认不重试。

断言与变量

状态码/Header/JSONPath/文本/时延断言；响应体先截断脱敏；变量提取只写入当前 Suite Run 内存。

发送结果

每 Case 发送 probe-result-v1；最终发送 SuiteCompleted。Producer 使用幂等模式；executionId+caseId+attempt 是结果唯一键。

06 · FAILURE RECOVERY

任务异常、卡死或无法正常结束怎么办

不依赖“进程最终会返回”。每个层级都有 deadline、Lease、Watchdog、重试上限和最终状态。

08 · PERFORMANCE EVIDENCE

如何证明压测确实达到 1W TPS

必须是开放模型、端到端、可对账、可复现的压测；不能用 Worker 自报 QPS，也不能只截一张瞬时峰值图。

压测拓扑

  1. 目标 Stub 集群与 Worker 分离，先证明 Stub 可稳定承受 ≥15k req/s。
  2. 使用 k6 constant-arrival-rate 或 wrk2 开放模型生成调度/目标负载，避免协调遗漏。
  3. 负载生成器至少 3 台，独立网卡与监控，避免 Generator 成为瓶颈。
  4. 固定代码 Git SHA、镜像 Digest、K8S YAML、Kafka/DB 配置、请求/响应大小和延迟分布。

四方对账

  1. Load Generator：planned / sent / accepted。
  2. Kafka：Command/Result offset 差值与重复率。
  3. Worker：started / completed / timeout，按 executionId+caseId。
  4. Result Store：唯一结果数、最终状态数和写入延迟。

必须满足：sent = unique completed + declared rejected/expired；任何无法解释的差值都视为丢失。

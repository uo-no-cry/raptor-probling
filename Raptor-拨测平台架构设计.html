01
SYNTHETIC MONITORING

拨测平台：HTTP 多环境主动探测

当前版本仅支持 HTTP/HTTPS 类型接口拨测。目标是从指定探测点验证应用各部署环境的网络可达性、HTTP 可用性与响应时延，并避免把网络未开通误判成应用故障。

功能范围

  • 仅支持 HTTP/HTTPS，支持 GET、HEAD 和受控 POST
  • 周期、手动、发布后触发
  • 按应用环境选择 URL 与探测点
  • 状态码、JSONPath/文本、时延断言
  • 连续失败与多点仲裁告警

非目标

  • 暂不支持独立 TCP、gRPC、DNS 和浏览器事务拨测
  • 不替代真实用户监控 APM
  • 不承载大响应体或压测流量
  • 不把网络不通或单次失败直接等价为应用事故
  • 不允许任意 URL 形成 SSRF 通道

SLO 建议

  • 调度准时率 ≥ 99.9%
  • 结果入库延迟 P99 ≤ 10s
  • 控制面月可用性 ≥ 99.9%
  • 探测结果至少一次送达

一次探测的完整链路

  1. 1
    环境与端点版本化

    保存 applicationId、environmentId、baseUrl、path、HTTP 方法、周期、超时、断言与密钥引用；发布后生成不可变 version。

  2. 2
    网络准入

    查询网络连通性矩阵；UNKNOWN/BLOCKED 不进入业务拨测队列，而是生成网络开通或复检任务。

  3. 3
    确定性调度

    Scheduler 以 executionId = taskId + environmentId + scheduledAt + probePoint 生成命令；Redis SET NX 或数据库租约防止重复投递。

  4. 4
    有界 HTTP 执行

    Worker 做 URL 白名单、DNS 重绑定防护、环境配额与响应体限制，记录 DNS/TCP/TLS/TTFB/总时延。

  5. 5
    结果分类

    区分 NETWORK_BLOCKED、DNS_ERROR、TLS_ERROR、HTTP_ERROR、ASSERTION_FAILED 与 TIMEOUT，避免故障归因混淆。

  6. 6
    告警判定

    采用连续 N 次失败、M/N 窗口和多探测点仲裁；状态机只在 OK↔FIRING 变化时通知。

CAPACITY MODEL“1W TPS”必须先解释口径
并发数 ≈ QPS × 平均耗时

若峰值到达率为 10,000 req/s、平均耗时 200ms，则同时在途约 2,000；若 P99 超时 3s，最坏在途可逼近 30,000。

单 Pod 安全吞吐500 req/s（压测假设）
峰值基础 Pod10,000 ÷ 500 = 20
冗余后建议26–30 Pods
HPA 信号Kafka lag + in-flight + CPU
保护阈值全局 / 租户 / 目标三级限流
结果数据量1KB × 10k/s ≈ 864GB/日（峰值若持续）

容量口径：系统按 1 万次 HTTP 探测请求/秒的突发目标设计；只有具备机器规格、持续时长、延迟分布和瓶颈记录的真实报告时，才可以称为“已压测验证”。

关键难点与解决方案

A

调度风暴与整点尖峰

难点大量分钟级任务在整分触发，Scheduler 和下游瞬时过载。

方案对周期任务增加确定性 jitter；分片调度器只负责生成命令，Kafka 削峰；设置租户配额与优先级队列。

取舍jitter 会让任务偏离整点，需要在产品上展示“计划时间”和“实际时间”。

B

重复执行与结果幂等

难点调度器故障转移、Kafka 重试会产生重复命令，网络调用本身不可事务化。

方案用稳定 executionId；Worker 允许至少一次执行，结果存储以 executionId 唯一键 upsert；通知以 incidentId + state 做幂等。

取舍不追求昂贵的端到端 exactly-once，而是在副作用边界做去重。

C

网络不通与应用故障混淆

难点应用刚部署到新环境但防火墙尚未开通，直接开始拨测会持续产生假告警。

方案维护应用—环境—探测点网络连通性矩阵；环境接入先做网络准入，BLOCKED/UNKNOWN 走网络开通流程；只有 REACHABLE 的链路才参与健康计算。

取舍引入额外状态与复检流程，但能把平台故障、网络故障和应用故障分层归因。

D

自动扩缩容滞后

难点只看 CPU 时，I/O 型 Worker 的 Kafka lag 已堆积但 CPU 仍不高。

方案KEDA/HPA 同时使用 lag、in-flight 和 CPU；保留最小热池；预估定时任务峰值做 scheduled scaling。

取舍多指标扩容更复杂，需要限制最大副本数并验证下游承载力。

E

SSRF 与凭据安全

难点允许用户配置 URL、Header 和脚本，可能访问元数据地址或泄露密钥。

方案目标必须属于应用目录；阻断私有保留地址和重绑定；Secret 只保存引用并在 Worker 运行时短期获取；响应体截断并脱敏。

取舍严格白名单会降低灵活性，例外需审批和审计。

01 · 需求规格说明书与功能设计摘录 展开
ID需求与验收标准优先级
REQ-ENV-001应用可维护标准或自定义环境；environmentId 稳定唯一，停用环境不再产生任务。P0
REQ-NET-001发布任务前必须存在有效的探测点—环境连通关系；无合法关系时返回 NOT_SCHEDULABLE。P0
REQ-HTTP-001仅支持 HTTP/HTTPS；默认 GET/HEAD，POST 必须是审批后的无副作用探测接口。P0
REQ-AST-001支持状态码、响应 Header、JSONPath/文本和总耗时断言；响应体读取有上限。P0
REQ-ALM-001连续失败且满足多探测点仲裁才告警；网络阻断与探测点故障不计为应用失败。P0
REQ-AUD-001配置、连通性、手动执行和告警操作均记录操作者、版本、时间与变更摘要。P1

功能页面：应用环境管理、HTTP 端点管理、网络连通性矩阵、拨测任务、执行记录、告警事件、审计日志。所有生产环境写操作均要求 RBAC 校验和审计。

02 · 接口设计文档与消息契约摘录 展开
接口 / Topic用途关键约束
POST /api/environments登记应用部署环境appId + code 唯一；prod 需要更高权限
PUT /api/connectivity/:id/verify触发网络连通性复检返回各阶段证据，不允许直接修改为 REACHABLE
POST /api/probes创建 HTTP 拨测定义校验 URL 归属、方法、副作用和 Secret 引用
POST /api/probes/:id/publish发布不可变配置版本无合法探测点时拒绝发布
probe-command-v1调度器向 Worker 下发执行命令携带 executionId、environmentId、probePointId、version、deadline
probe-result-v1Worker 返回结构化结果错误分类、分阶段耗时、断言结果；executionId 幂等
ProbeCommandV1 {
  executionId, taskId, version,
  applicationId, environmentId, probePointId,
  method, url, headersRef, bodyRef,
  timeoutMs, assertions[], scheduledAt, deadline
}
03 · 开发实现计划与完成定义 展开
Iteration 1

应用环境、HTTP Endpoint、网络矩阵 CRUD 与 RBAC。

Iteration 2

ElasticJob 分片调度、Kafka Command、幂等键和过期任务处理。

Iteration 3

Go HTTP Worker、连接池、分阶段计时、断言与 SSRF 防护。

Iteration 4

结果聚合、告警状态机、Slack 通知、查询页面与审计。

Iteration 5

HPA/KEDA、自监控、容量验证、灰度开关和 Runbook。

Definition of Done：需求与设计可追踪；测试先行；代码评审完成；单元、契约和集成测试通过；无 Critical/High 安全问题；数据库迁移向后兼容；指标、日志、告警和运维文档随代码交付。

05 · 上线方案、验收报告与复盘报告摘录 展开
上线方案
  • Shadow 模式：只记录不告警
  • 非生产试点应用
  • 预发扩大覆盖
  • 少量生产只读健康接口
  • 分批全量并保留停止条件
回滚条件
  • 出现未授权网络访问
  • 调度或结果延迟突破阈值
  • 批量假阳性告警
  • Kafka 积压持续扩大
  • 数据库或下游被明显拖慢
验收报告
  • 需求追踪矩阵全部闭环
  • P0/P1 缺陷满足准出要求
  • 技术、安全、业务验收意见
  • 遗留问题与整改期限
  • SLO 正式统计起点
复盘报告
  • 目标与实际指标对照
  • 问题时间线与促成因素
  • 保护机制为何生效或失效
  • 行动项、角色 Owner、期限
  • 文档与测试更新记录

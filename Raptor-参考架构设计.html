01
SYNTHETIC MONITORING

拨测平台：HTTP 多环境主动探测

当前版本仅支持 HTTP/HTTPS 类型接口拨测。目标是从指定探测点验证应用各部署环境的网络可达性、HTTP 可用性与响应时延，并避免把网络未开通误判成应用故障。

功能范围

  • 仅支持 HTTP/HTTPS，支持 GET、HEAD 和受控 POST
  • 周期、手动、发布后触发
  • 按应用环境选择 URL 与探测点
  • 状态码、JSONPath/文本、时延断言
  • 连续失败与多点仲裁告警

非目标

  • 暂不支持独立 TCP、gRPC、DNS 和浏览器事务拨测
  • 不替代真实用户监控 APM
  • 不承载大响应体或压测流量
  • 不把网络不通或单次失败直接等价为应用事故
  • 不允许任意 URL 形成 SSRF 通道

SLO 建议

  • 调度准时率 ≥ 99.9%
  • 结果入库延迟 P99 ≤ 10s
  • 控制面月可用性 ≥ 99.9%
  • 探测结果至少一次送达

一次探测的完整链路

  1. 1
    环境与端点版本化

    保存 applicationId、environmentId、baseUrl、path、HTTP 方法、周期、超时、断言与密钥引用；发布后生成不可变 version。

  2. 2
    网络准入

    查询网络连通性矩阵；UNKNOWN/BLOCKED 不进入业务拨测队列，而是生成网络开通或复检任务。

  3. 3
    确定性调度

    Scheduler 以 executionId = taskId + environmentId + scheduledAt + probePoint 生成命令；Redis SET NX 或数据库租约防止重复投递。

  4. 4
    有界 HTTP 执行

    Worker 做 URL 白名单、DNS 重绑定防护、环境配额与响应体限制，记录 DNS/TCP/TLS/TTFB/总时延。

  5. 5
    结果分类

    区分 NETWORK_BLOCKED、DNS_ERROR、TLS_ERROR、HTTP_ERROR、ASSERTION_FAILED 与 TIMEOUT，避免故障归因混淆。

  6. 6
    告警判定

    采用连续 N 次失败、M/N 窗口和多探测点仲裁；状态机只在 OK↔FIRING 变化时通知。

CAPACITY MODEL“1W TPS”必须先解释口径
并发数 ≈ QPS × 平均耗时

若峰值到达率为 10,000 req/s、平均耗时 200ms，则同时在途约 2,000；若 P99 超时 3s，最坏在途可逼近 30,000。

单 Pod 安全吞吐500 req/s（压测假设）
峰值基础 Pod10,000 ÷ 500 = 20
冗余后建议26–30 Pods
HPA 信号Kafka lag + in-flight + CPU
保护阈值全局 / 租户 / 目标三级限流
结果数据量1KB × 10k/s ≈ 864GB/日（峰值若持续）

容量口径：系统按 1 万次 HTTP 探测请求/秒的突发目标设计；只有具备机器规格、持续时长、延迟分布和瓶颈记录的真实报告时，才可以称为“已压测验证”。

关键难点与解决方案

A

调度风暴与整点尖峰

难点大量分钟级任务在整分触发，Scheduler 和下游瞬时过载。

方案对周期任务增加确定性 jitter；分片调度器只负责生成命令，Kafka 削峰；设置租户配额与优先级队列。

取舍jitter 会让任务偏离整点，需要在产品上展示“计划时间”和“实际时间”。

B

重复执行与结果幂等

难点调度器故障转移、Kafka 重试会产生重复命令，网络调用本身不可事务化。

方案用稳定 executionId；Worker 允许至少一次执行，结果存储以 executionId 唯一键 upsert；通知以 incidentId + state 做幂等。

取舍不追求昂贵的端到端 exactly-once，而是在副作用边界做去重。

C

网络不通与应用故障混淆

难点应用刚部署到新环境但防火墙尚未开通，直接开始拨测会持续产生假告警。

方案维护应用—环境—探测点网络连通性矩阵；环境接入先做网络准入，BLOCKED/UNKNOWN 走网络开通流程；只有 REACHABLE 的链路才参与健康计算。

取舍引入额外状态与复检流程，但能把平台故障、网络故障和应用故障分层归因。

D

自动扩缩容滞后

难点只看 CPU 时，I/O 型 Worker 的 Kafka lag 已堆积但 CPU 仍不高。

方案KEDA/HPA 同时使用 lag、in-flight 和 CPU；保留最小热池；预估定时任务峰值做 scheduled scaling。

取舍多指标扩容更复杂，需要限制最大副本数并验证下游承载力。

E

SSRF 与凭据安全

难点允许用户配置 URL、Header 和脚本，可能访问元数据地址或泄露密钥。

方案目标必须属于应用目录；阻断私有保留地址和重绑定；Secret 只保存引用并在 Worker 运行时短期获取；响应体截断并脱敏。

取舍严格白名单会降低灵活性，例外需审批和审计。

CLAUDE CODE TOOLING

Sumo Logic 日志查询插件

把自然语言意图转换为受控查询，而不是把 Sumo Token 或任意查询权限直接交给模型。插件更适合实现为本地 MCP Server / Claude Code 工具集。

TRUST BOUNDARY模型能“请求工具”，不能越过策略网关
Developer描述故障与应用
→
Claude Code选择工具 · 解释结果
typed args→
Local MCP Serverschema · redaction · audit
mTLS / OAuth→
Raptor GatewayRBAC · scope · rate limit
→
Sumo Logic APISearch Job · Page
resolve_app()

把应用名解析为 sourceCategory、环境和用户可见范围，避免模型猜索引。

search_logs()

只接受 app、env、timeRange、keywords、level、limit 等结构化参数。

get_search_page()

分页读取搜索结果；默认 limit 100、最大时间窗 2h，避免一次性拉取海量日志。

summarize_errors()

在网关侧按错误指纹聚合、脱敏和采样，再返回给模型，减少上下文与泄露面。

查询协议

search_logs({
  app: "payment-api",
  env: "prod",
  timeRange: { from: "-30m", to: "now" },
  filters: { level: ["ERROR"], keyword: "timeout" },
  limit: 100
})

→ { searchId, status, rows[], nextCursor, querySummary }

安全控制

  • 授权继承用户身份透传，按 app owner / on-call / environment 校验。
  • 查询约束服务端拼装 DSL，拒绝任意 source、子查询和超长时间窗。
  • 字段脱敏Token、Cookie、手机号、邮箱和业务敏感字段规则化遮蔽。
  • 审计留痕记录用户、应用、时间窗、规范化查询哈希、行数与结果状态，不落完整日志正文。

关键难点与解决方案

A

自然语言查询不可控

难点模型可能生成全局、长时间窗或高成本 DSL。

方案把工具参数设计成封闭 schema；应用范围来自 Raptor 元数据；由服务端模板生成最终 DSL 并估算成本。

取舍牺牲任意查询表达力，换取稳定性与权限可证明性。

B

异步 Search Job

难点Sumo 查询通常需要创建 Job、轮询状态、再分页读取，Claude 单次工具调用容易超时。

方案create/search/status/page 分段；返回 searchId 与 cursor；短查询可在网关内有限轮询，超时后让 Claude 继续调用。

取舍多轮工具调用略显繁琐，但避免长连接和不可控等待。

C

日志量超出上下文

难点原始日志重复且体量大，直接返回既贵又难定位。

方案服务端按 fingerprint 聚类、头尾采样、字段裁剪；优先返回趋势和代表样本，用户确认后再下钻。

取舍聚合可能隐藏罕见样本，因此保留 cursor 和原始事件 ID。

D

提示注入（Prompt Injection）与敏感信息

难点日志正文是不可信输入，可能包含伪指令或凭据。

方案工具结果标记为 untrusted data；不允许日志内容触发其他工具；脱敏后再返回；高敏环境默认禁用正文导出。

取舍无法完全依赖模型遵守，关键边界必须在网关强制。

将应用元数据、拨测证据和用户输入组合为结构化工单。默认只生成草稿；真正创建工单属于有副作用操作，必须二次确认。

用户Claude / MCPRaptorJira

2补充影响→draft_ticket→校验必填字段与证据链接
3确认草稿→create_ticket→幂等创建并返回 Jira Key
INPUT

结构化事实

appId、环境、变更类型、影响范围、时间窗、日志/拨测证据 ID、期望完成时间。

POLICY

模板与路由

OUTPUT

可审阅草稿

标题、背景、影响、复现步骤、验收标准、回滚方案与附件链接；明确标注模型推断项。

关键难点与解决方案

A

幻觉写入正式工单

难点模型可能把不确定信息当作事实，造成错误优先级、错误责任人或无效工单。

方案字段标注 source：user / raptor / inferred；inferred 字段在 UI 高亮；create 前返回完整草稿并要求确认。

取舍多一步确认，但把不可逆副作用留给用户决策。

B

重复创建

难点网络超时后重试 create，可能生成多个相同 Ticket。

方案clientRequestId 作为幂等键；Raptor 保存 requestId→jiraKey；Jira description/property 同时写入关联 ID。

取舍幂等记录需设置合理 TTL，并处理用户确实想重开工单的场景。

C

字段动态且项目差异大

难点不同 Jira Project 的必填字段、工作流和选项不同，硬编码很快失效。

方案定时同步 Jira metadata；按 project + issueType 缓存 schema；创建前实时校验，失败时返回可修复字段而非裸 API 错误。

取舍需要管理 schema 版本与缓存失效。

D

权限与附件泄露

难点日志证据可能包含敏感数据，工单可见范围可能比日志系统更大。

方案默认附短期授权链接而非复制正文；按目标项目可见性校验证据；服务账号仅拥有白名单项目创建权限。

取舍证据链接过期会影响复盘，可用受控归档替代长期公开附件。

关键难点与解决方案

A

模板演进与历史可追溯

难点模板可编辑后，无法解释历史消息为何长这样，也难以安全回滚。

方案模板发布即生成不可变版本；Delivery 固化 templateVersion、routeId 和渲染变量哈希；草稿、发布、废弃走状态流。

取舍版本数量增加，需要清理未发布草稿但保留已使用版本。

B

事务成功但通知事件丢失

难点业务提交成功后直接调用 Slack，进程崩溃会丢消息；先发消息又可能出现业务回滚但通知已发。

方案业务数据与 Outbox 在同一 MySQL 事务提交；Relay 异步发布 Kafka；发送链路与核心事务解耦。

取舍Outbox 增加表和 Relay 运维成本，但能明确解决双写一致性。

C

Channel 配置漂移

难点Channel 被归档、Bot 被移除或不同环境误投到同一频道。

方案保存 channelId 而非名称；配置发布时调用 Slack 校验；生产与非生产路由加环境约束；定期健康检查。

取舍依赖 Slack API 可用性，配置校验需缓存并允许受控降级。

D

重复消息与顺序

难点Kafka 重投、网络超时和多个消费者会导致重复；同一事故恢复消息可能先于告警到达。

方案eventId + routeId 唯一约束；按 fingerprint 分区；Delivery 状态用乐观锁；Slack client_msg_id/本地回执辅助去重。

取舍只能保证同一 key 局部顺序，跨事件全局顺序没有必要且代价高。

E

限流和级联故障

难点大面积故障会同时产生海量通知，Slack 429 反过来拖垮业务线程。

方案业务只写 NotificationEvent；独立消费者按 workspace/channel 令牌桶限流；合并同指纹事件；重试队列与 DLQ 隔离。

取舍非紧急消息可能延迟，需按 severity 设计优先级。

高频追问速查

为什么 Kafka 不直接用 ElasticJob 调 Worker？

ElasticJob 适合分布式定时触发，但不擅长承接高峰背压。让它只生成命令，Kafka 负责削峰、重放和消费组扩展，执行面更容易故障隔离。

怎么证明 1W TPS？

说明压测模型：目标响应延迟分布、连接复用比例、Pod 规格、持续时长、错误率、P99、Kafka lag 和下游是否被 mock。没有压测报告就只能称“设计目标”。

为什么结果不是 exactly-once？

网络调用无法纳入 Kafka 事务。使用至少一次投递，在结果、工单和通知这些副作用边界用稳定幂等键去重，复杂度更可控。

Claude Code Plugin 与 MCP 是什么关系？

可把“插件”落成一个本地 MCP Server：暴露少量类型化工具，由 Raptor 网关做真正授权和审计。模型不持有 Sumo/Jira 的宽权限 Token。

日志里的提示注入怎么处理？

日志是非可信数据。工具结果需明确隔离；日志文本不能决定调用其他工具；服务端脱敏、限字段、限行数，敏感操作仍需用户确认。

Slack 模板为什么要版本化？

为了回溯“哪条消息用了哪个模板和路由”，支持灰度与回滚，并避免编辑模板导致历史投递不可解释。
